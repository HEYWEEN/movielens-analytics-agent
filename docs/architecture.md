# 架构与后续迭代接入约定

## 当前形态

本项目保持模块化单体。前端与 API 在一个进程；清洗作业由执行适配层调用本地 Python 或 Hadoop Streaming；SQLite 保存任务状态，文件系统保存产物。当前只有 `governance.clean_and_assess` 一项已注册工具。工具注册不等于已实现第二、三轮算法。

## 核心边界

1. **Agent/HTTP** 解析请求、选择已登记工具、返回任务状态和基于报告的解释，不直接计算评分。
2. **工具** 声明输入和输出类型。治理工具要求原始数据，输出清洗数据、质量报告和未核验冲突证据。
3. **执行适配** 负责本地或 Hadoop 作业及错误传播；不得在执行失败时发布成功状态。
4. **任务存储** 保存状态、阶段事件和失败原因；重启后将中断任务标为失败。当前只允许一个运行中的任务。
5. **产物清单** 保存文件摘要和关键版本。下游必须先校验清单，再读取文件。文件名和任务完成状态本身不足以证明内容未变。

## 后续迭代的接入步骤

第二轮每个算法独立注册工具，输入应是经过清单验证的清洗数据版本、未核验冲突记录及相同的 `T1/T2`。模型、特征、用户画像、聚类和降维坐标应分别发布清单，记录上游产物 ID、参数和评价指标。训练输入只能来自 `T1` 之前的数据。

第三轮先构建和校验图谱，再让推荐、图挖掘、链接分析工具引用**同一个已校验图谱版本或其投影**。图谱产物需记录上游清洗数据及第二轮产物版本。图谱缺失、校验失败或版本不一致时，工具拒绝运行。

未来增加工具时，应补齐：输入契约、版本检查、状态与失败语义、输出文件摘要、验证规则、最小集成测试。当前 `manifest.json` 仅覆盖第一轮文件，尚不是完整的跨迭代依赖目录；第二轮开始前应扩展清单格式并迁移现有报告。

## 当前限制

Hadoop Streaming 把所有记录送到一个 reducer，适合课程数据规模但不具备横向扩展性。任务执行线程和 SQLite 都运行在单服务进程内，适合单机演示；若需要多实例或可靠队列，应先将任务执行与 API 分离，并明确幂等和恢复策略。无需仅为课程规模提前加入微服务、HBase 或图数据库。
